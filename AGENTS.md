# LLM-Assisted Proving

Guidelines and prompts for using LLMs to write and refactor Lean 4 proofs in this repository.

## Proof style
- Attribute-generated lemmas
  - Read `sympy/Basic.lean` to understand attribute-generated lemmas (`@[comm]`, `@[cast]`, `@[mp]`, `@[mpr]`, `@[fin]`, `@[mt]`, …) and apply them wisely.
  - For `LHS.is.RHS` tagged with `@[mp]` / `@[mpr]`, prefer the generated one-direction lemmas `RHS.of.LHS` / `LHS.of.RHS` over calling `.mp` / `.mpr` on the iff.
  - For `LHS.eq.RHS` tagged with `@[comm]`, prefer the generated commutative lemma `RHS.eq.LHS` over `simp [← LHS.eq.RHS]` or `rw [LHS.eq.RHS.symm]`.
  - Run `python py/docstring.py <leanFile>` if necessary. It'll generate the attribute docstring table if the lemma uses attributes other than `@[main]`.
- code layout strictly 2-indented
  - before the `given` section, 
    - omit auto-bound implicits
    - list in order:
      - line(s) of standalone instances (instImplicit)
      - line(s) of implicit binder(s) and their dependent instances (instImplicit) on the same line, if any
      - line(s) of bare implicit binders
  - default arguments should be put within the `given` section: propositions come first, expressions come next, unless otherwise specified
  - arguments of the same type should be combined, eg: {a b: Type} or (a b: Type)
  - conclusion must be put within the `imply` section
  - proof body must be put within the `proof` section, within proof:
    - binary operators below should not be indented by new lines:
      - `:`, e.g., (ident : Type) 
      - arithmetic operators: `+` `-` `*` `/` 
      - relational operators: `=` `≠` `>` `<` `≥` `≤` 
    - After a bullet tactic (`·`), put the next statement on a new line when that branch contains more than one step.
    - tactics convention:
      - Use `obtain` instead of `rcases`, `if … then … else …` instead of `by_cases` (if it is not followed by `<;>`), `have` instead of `haveI`, and `let` instead of `letI`.
      - inline `have` without introducing `show` if it is referenced only once, e.g.: prefer `apply` instead of `exact`, perhaps by creating some holes.
      - use `calc` instead of `by calc`, start `calc` with `_`
      - avoid `calc` within [] block of `rw`/`erw`/`simp`, or within () as arguments;
      - no multi-line tactics inside parentheses, the tactic within compact type-ascribed `by` term (by tactic : Type) should be one-liner with no `;`
      - follow `show` with `from`/`by` instead of `from by`
      - `by exact expr` should be simplifed to `expr`
      - use `grind`/`aesop` as much as possible
      - use `_` as unused binders or unnamed holes, prefer `_` instead of `?_`/`?identifier`
  - date created must be today, if date updated is the same as date created, it should be omitted.
- [lemma path](mjs/README.md)
  - it conveys the lemma semantic per se, thus facilitating search
  - suggest a better lemma path if it isn't consistent with what is suggested by mjs/lemmaPath.mjs
- `import` statements
  - check py/delete_import.py to simplify `import` statements
- `open` statements
  - check delete_open.* to simplify `open` statements
  - use `open Section` if lemmas from that Section are imported


## Sympy concrete sum sugar
- Process-at-index finite sums live in `sympy/concrete/summations.lean` (mirrors sympy `summations.py`; formerly `sum_at.lean`).
- Import `sympy.concrete.summations`. Syntax: `∑ «a.bvar» t, body` elaborates to `∑ c, body'` with `«a.bvar» t` replaced by `c` (not a sum over `ℕ → A`).

## Sympy 𝔼 conditioning sugar (`sympy/stats/joint_rv.lean`)
- Observation forms are unchanged: `𝔼[x: π](f x | y = y0)` (event conditioning `Expectation.condEvent`), `| y = y0 ∧ z = z0`, `𝔼[x: π | y](… | r = r0)` (`partialRV_cond`).
- Random-argument form (no `=` after `|`), since 2026-10-06: `𝔼[x, …: π](body | y₁, …, yₙ)` is the **σ-algebra** conditional expectation `Expectation.condSigma π joint (y₁, …) (fun … ↦ body)`, by definition (`Expectation.condSigma_eq_condExp`, `rfl`) Mathlib's `π[fun ω ↦ body[x := asRV x ω] | MeasurableSpace.comap (y₁, …) inferInstance]`: no density, no atoms; compare with `=ᵐ[π]`. The `yᵢ` are arbitrary terms `Ω → _` (precedence 51, outside the binder scope, e.g. `| s t, a t, s (t + 1)`), packed right-nested by `JointRandomSymbol`; write `(y, z), w` for left nesting. Lemma paths name it `Expect` (lemmaPath).
- Removed 2026-10-06 (breaking): the event-RA meaning of `𝔼[x: π](f | y)` (`Expectation.condEventRA`), the unused density `Expectation.condRA`, the bracket form `𝔼[x: π | y](body | r, s)`, and the short-lived `∥` separator. For "free RVs + random arguments" integrate the free RVs too: `𝔼[x, y: π](f x y | y, r)`. The density def `Expectation.partialRV_RA` is kept (no sugar) because `Random.Expect_Cond.ae.Expect` / `Random.Expect_Cond.eq.Expect` state their results with it by name.
- Conditional independence sugar `X ⟂ᵢ[π] Y | Z` (since 2026-10-06, defined after `Expectation.asRV`): `ProbabilityTheory.CondIndepFun (MeasurableSpace.comap Z inferInstance) _ X Y π` (needs `StandardBorelSpace Ω`, `IsFiniteMeasure π`). If `X` is a process `ℕ → Ω → α`, e.g. the slice `r[t + 1:]`, it is read as the path RV `Expectation.asRV X = fun ω k ↦ X k ω` (elaborator `condIndepLeft%`); any other `X` is kept syntactically unchanged, so existing `rw`/`simp` proofs still match. `Measurable Z` is found by `assumption` or `apply_assumption` (so `h₁ : ∀ t, Measurable (s t)` covers `| s (t + 1)`), or by the tactic `measurable_component` (defined in `sympy/stats/joint_rv.lean`, since 2026-10-06) as a component `.fst` / `.snd` / `.snd.fst` / `.snd.snd` / … of a (∀-quantified) joint measurability hypothesis (so `h₁ : ∀ t, Measurable (r t, s t, a t)` covers `| s (t + 1)` too). A pair `(s t, a t)` in the `Y` slot elaborates to `JointRandomSymbol (s t, a t).1 (s t, a t).2`.
- Conditional independence → dropping a conditioner: `Random.MEqExpect.of.CondIndep.Integrable.Measurable.Measurable.Measurable.Measurable` (`F ⟂ᵢ[π] X | Z`, measurable `F X Z g`, `g ∘ F` integrable ⇒ `𝔼[F: π](g F | X, Z) =ᵐ[π] 𝔼[F: π](g F | Z)`).

## Sympy random-variable lifting sugar (`sympy/stats/joint_rv.lean`, since 2026-10-06)
- `rv%[μ] x` reads `x` as a random variable on `Ω` (`μ : Measure Ω`): a function applied to random variables is lifted pointwise, e.g. `rv%[π] (V t (s t))` ↦ `fun ω ↦ V t (s t ω)`, `rv%[π] (Q t (s t) (a t))` ↦ `fun ω ↦ Q t (s t ω) (a t ω)`, `rv%[π] (u X)` ↦ `fun ω ↦ u (X ω)`. The result is syntactically the hand-written lambda (binder `ω`), so proofs see no difference.
- Both sides of Mathlib's `f =ᵐ[μ] g` go through `rv%[μ]` (an extra `macro_rules` on Mathlib's syntax, no new notation), so write `∀ t, V t (s t) =ᵐ[π] 𝔼[r: π](… | s t)` instead of `∀ t, (fun ω ↦ V t (s t ω)) =ᵐ[π] …`.
- Fallback only: `x` is elaborated as is first (normal elaboration order, postponement passed through); only on a real error are the local names of type `Ω → α`, `ℕ → Ω → α`, `Fin n → Ω → α` in `x` rebound to their values at `ω`; if that fails too, the original error is reported. Every `=ᵐ` that elaborated before is unchanged. Not lifted: global constants, other index types, `μ` given as `_`.
- lemmaPath names the lifted LHS like an ordinary `=ᵐ` (`AeEq` ↦ README `MEq`), e.g. `∀ t, V t (s t) =ᵐ[π] 𝔼[…]` is `All_MEq_Expect`.

## Sympy tuple history slice (`sympy/stats/hidden_markov_sequence.lean`, since 2026-10-06)

- `(r, s, a)[:n]` (a literal tuple of processes `ℕ → Ω → _`, prefix slice) expands by `macro_rules` on `stdlib.List`'s `x[:stop]` syntax to `fun ω (i : Fin n) ↦ (r i, s i, a i) ω : Ω → Fin n → ℝ × S × A` — syntactically the hand-written term (`==`-equal after elaboration), so proofs are unaffected. Pairs/triples use the tuple coercion, ≥ 4 components right-nested `JointRandomSymbol`. Only a literal tuple receiver is rewritten; `x[:n]` on a single process, lists, vectors, tensors or a parenthesized `(e)[:n]` keep the generic `x.getSlice ⟨0, n, 1⟩`. Needs `import sympy.stats.hidden_markov_sequence`. lean.js renders it as `(r, s, a)_{:n}`. Works as the right operand of `⟂ᵢ`, e.g. `(a n, r n, s (n + 1)) ⟂ᵢ[π] (r, s, a)[:n] | s n`.

## Debugging
- print logging info via `sympy.printing.echo` by creating *.echo.lean tracing files for debugging.
- Confirm the file compiles with `lake build <Module.Name>` or `lake env lean <path/to/file.lean>`.
- The web compile (`server/lean/echo2vue.mjs`) re-serializes the file through the JS parser (`static/js/parser/lean.js`) into `*.echo.lean` before `lake env lean`; `lake build` being green is not enough. Known serializer breakages (2026-10-06): an inline term-mode `by tac <;> tac` (e.g. `fun ω ↦ by by_cases h : ω ∈ s <;> simp [h]`) and a trailing `-` clear pattern (`rintro _ ⟨D, hD, rfl⟩ -`, which swallows the next line); a trailing `-- comment` after a hypothesis in the signature (`(h₁ : …) -- note`) used to wreck the signature (fixed in lean.js 2026-10-06: it now compiles and `mjs/lemmaPath.mjs` parses it; the `*.echo.lean` still moves the comment onto its own line below the hypothesis). Prefer term proofs / multi-line tactic blocks and `_` instead of `-`.
